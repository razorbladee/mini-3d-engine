## 1. P0 — блокеры

### P0-1. `npm run build` падает: спред в `Vector3.set()`

**Файл:** `src/loaders/GLTFLoader.ts` (метод `build`, лямбда `apply`)

```
src/loaders/GLTFLoader.ts(3,3602): error TS2556: A spread argument must either have a tuple type or be passed to a rest parameter.
src/loaders/GLTFLoader.ts(3,3643): error TS2556: A spread argument must either have a tuple type or be passed to a rest parameter.
```

Причина: `t.position.set(...n.translation)` и `t.scale.set(...n.scale)`, где `n` имеет тип `any`,
а `Vector3.set` принимает ровно три аргумента.

**Требование.** Явно разворачивать компоненты и валидировать длину массива:
`const [x, y, z] = n.translation; if (![x,y,z].every(Number.isFinite)) throw …; t.position.set(x, y, z);`

**Критерий приёмки.** `npx tsc --noEmit` завершается с кодом 0 на `src`, `examples` **и** `tests`.

### P0-2. Индекс аксессора `0` считается отсутствующим — ломается загрузка почти любого glTF

**Файл:** `src/loaders/GLTFLoader.ts`, метод `build`

```ts
for (const prim of m.primitives ?? []) { if (!prim.attributes?.POSITION) continue; … }
```

`POSITION: 0` — валиднейший и самый частый случай в реальных файлах, но `!0 === true`,
поэтому примитив молча пропускается, меш не создаётся, и загрузка падает с
`glTF scene contains no renderable meshes`.

**Воспроизведение (замерено):** тест `tests/loader.test.ts > finds orphan mesh nodes and supports
multiple primitives` падает именно по этой причине. Инструментированный прогон печатает
`skip prim` для обоих примитивов, при том что `read()` для аксессора 0 отрабатывает корректно
и возвращает `{values:[0,0,0,1,0,0,0,1,0],count:3,size:3}`.

**Требование.** Всюду в лоадере заменить проверки на «truthy» проверкой на `undefined`/`null`:
`if (prim.attributes?.POSITION === undefined) continue;`. Провести полный аудит файла на такие же
ошибки (`prim.indices !== undefined` — уже корректно, `json.scene ?? 0` — корректно,
`buffers[b?.buffer ?? 0]` — потенциально маскирует ошибку и требует явной проверки).

**Критерий приёмки.** Тест на аксессор с индексом `0` (POSITION, NORMAL, TEXCOORD_0, indices —
все четыре) проходит; загрузка `BoxAnimated.gltf` в showcase даёт видимую геометрию.

## 2. P1 — дефекты рантайма

### P1-1. Ambient- и Hemisphere-свет полностью игнорируются рендерером

**Файл:** `src/rendering/WebGLRenderer.ts`, `createProgram`

Имена uniform-локаций собираются эвристикой по подстроке:

```ts
`u${Key}${key.includes('Color') || key.includes('Direction') || key.includes('Intensity') ? '[0]' : ''}`;
```

Для `ambientColor` эвристика выдаёт `uAmbientColor[0]`, но в шейдере это **не массив**:
`uniform vec3 uAmbientColor;`. `getUniformLocation` для несуществующего активного имени возвращает
`null`, `gl.uniform3fv(null, …)` — no-op. Итог: весь вклад `AmbientLight` и `HemisphereLight`,
который аккуратно считается в `collectLights`, выбрасывается, а сцена освещается только
шейдерным фолбэком `max(uAmbientColor, vec3(.12))`.

Побочно: та же эвристика даёт `uPointPosition` и `uPointDistance` **без** `[0]`, тогда как
остальные массивы — с ним. Работает по спецификации, но непредсказуемо и нечитаемо.

**Требование.** Убрать эвристику. Ввести явную таблицу-описание uniform-ов:

```ts
const LIT_UNIFORMS = {
  roughness: 'uRoughness',
  ambientColor: 'uAmbientColor',
  directionalColor: 'uDirectionalColor[0]',
  …
} as const satisfies Record<string, string>;
```

и типизировать `ProgramState` как `Record<keyof typeof LIT_UNIFORMS, WebGLUniformLocation | null>`
вместо текущего `const state: any`.

**Критерий приёмки.** Юнит-тест с fake-`WebGL2RenderingContext` фиксирует полный список
запрошенных имён uniform-ов и сверяет его с именами, реально объявленными в
`shaders.ts` (парсинг источника регэкспом `uniform\s+\w+\s+(\w+)(\[|;)`). Ни одного запроса
несуществующего имени.

### P1-2. OrbitControls: неверный порядок вращения — камера смотрит мимо цели до 14.6°

**Файлы:** `src/interaction/OrbitControls.ts` + `src/math/Matrix4.ts`

`updateCamera()` ставит позицию на сфере вокруг цели и задаёт
`camera.rotation.set(-elevation, azimuth, 0)`. Но `Matrix4.compose` строит матрицу
в порядке **XYZ** (проверено численно: расхождение с `Rx·Ry·Rz` = 2.5e-8, с остальными
порядками — 1e-1…2.2e-1). Для орбитальной камеры требуется **YXZ** (`Ry(azimuth)·Rx(-elevation)`).

**Замер.** При `azimuth = 0.9`, `elevation = 0.6` угол между forward-вектором камеры и
направлением на цель:

| Порядок          | Ошибка      |
| ---------------- | ----------- |
| XYZ (текущий)    | **14.576°** |
| YXZ (правильный) | 0.000°      |

Цель уезжает из центра кадра при любом одновременно ненулевом azimuth и elevation, что
затрагивает **все** 3D-сцены витрины.

**Требование.**

1. `Euler.order` перестаёт быть декоративной строкой: `Matrix4.compose` обязан её учитывать.
   Минимум — поддержать `XYZ` и `YXZ`; предпочтительно — все шесть порядков.
2. Либо (предпочтительный вариант) — реализовать `Camera.lookAt(target, up)`, которого требует
   `MVP-SPEC.md` §4.6 и которого сейчас нет, и переписать `OrbitControls.updateCamera` через него.
3. `OrbitControls` не должен молча зависеть от внутреннего порядка углов `Matrix4`.

**Критерий приёмки.** Тест: для сетки из ≥20 комбинаций `azimuth × elevation` угол между
forward-вектором камеры и вектором «камера → target» < 1e-6 рад.

### P1-3. CapsuleGeometry: 94% треугольников вывернуты, 40 вырожденных

**Файл:** `src/geometry/CapsuleGeometry.ts`

Инструментированный обход (сверка знака `cross(b-a, c-a)` с записанной нормалью вершины):

| Примитив    | Треугольников | Вывернутых | Вырожденных |
| ----------- | ------------- | ---------- | ----------- |
| Box         | 12            | 0          | 0           |
| Sphere      | 256           | 0          | **32**      |
| Cylinder    | 96            | 0          | 0           |
| Torus       | 1024          | 0          | 0           |
| **Capsule** | 680           | **640**    | **40**      |

При `gl.enable(CULL_FACE)` + `frontFace(CCW)` капсула отбраковывается по граням — то есть
`advanced-primitives` сцена показывает вывернутую наизнанку/невидимую капсулу.

Причина — порядок вершин в развёртке: `[v(row,a0), v(row+1,a1), v(row,a1), v(row,a0), v(row+1,a0), v(row+1,a1)]`.
Вырожденные треугольники — вырождение колец на полюсах (`r = 0`), там же у сферы.

**Требование.**

1. Исправить намотку капсулы на CCW.
2. Не эмитить треугольники с нулевой площадью на полюсах (полярные кольца дают треугольники,
   а не квады) — и для `CapsuleGeometry`, и для `SphereGeometry`.
3. Ввести общий хелпер `assertGeometryIntegrity(geometry)` (только в dev/тестах).

**Критерий приёмки.** Существующий тест `has no degenerate triangles` проходит без правок,
плюс новый тест `winding matches vertex normals`: для каждого примитива 0 вывернутых треугольников.

### P1-4. `Frustum` не работает вообще

**Файл:** `src/interaction/Frustum.ts`

Плоскости строятся из **захардкоженных** нормалей `[-1,0,0]`, `[1,0,0]`, `[0,-1,0]`… с подстановкой
`m[3] ± m[0]` в дистанцию. Это не извлечение плоскостей Gribb–Hartmann: там нормали берутся из
**строк** матрицы `P·V` (`row3 ± row0` и т. д.), а не назначаются фиксированно. Дополнительно
сама композиция `m = P·V` в цикле выполнена в перепутанном порядке индексов.

**Замер.** Камера в `(0,0,5)`, fov 60, near 0.1, far 100:

| Точка                           | Ожидание | Факт        |
| ------------------------------- | -------- | ----------- |
| `(0,0,0)` — прямо перед камерой | `true`   | **`false`** |
| `(0,0,50)` — позади             | `false`  | `false`     |
| `(500,0,0)` — далеко вне        | `false`  | `false`     |

Метод не возвращает `true` никогда — то есть culling на его основе скрыл бы всю сцену.
Тест `roadmap.test.ts > tests frustum points` красный и фиксирует именно это.

**Требование.** Переписать `setFromCamera` через корректное извлечение плоскостей из
`viewProjection` (`clip = P · V`, плоскости = `row3 ± row_i`, с нормализацией), с сохранением
column-major раскладки. `intersectsSphere` и `intersectsPoint` — соответственно.

**Критерий приёмки.** Табличный тест: точка в центре кадра, точка за near, точка за far, точка
за левой границей, сфера, частично пересекающая границу, — 5+ кейсов с ожидаемыми значениями.

### P1-5. GLTFLoader: неверная конвертация кватерниона в углы Эйлера

**Файл:** `src/loaders/GLTFLoader.ts`, лямбда `apply`

Используется классическая формула yaw/pitch/roll (**ZYX**-порядок, «авиационный»),
а результат кладётся в `Euler`, который `Matrix4.compose` интерпретирует как **XYZ**.

**Замер.** Для кватерниона поворота на 1.1 рад вокруг оси `(0.3, 0.5, -0.8)`:

```
эталонная R : 0.504,-0.637,-0.584, 0.804, 0.593, 0.047, 0.316,-0.493, 0.810
полученная  : 0.504,-0.762,-0.407, 0.637, 0.646,-0.421, 0.584,-0.047, 0.810
max err     : 4.68e-1
```

Любой glTF-узел с ненулевым `rotation` (то есть большинство реальных моделей) ставится в сцену
с грубо неправильной ориентацией.

**Требование.** Не конвертировать кватернион в углы. `Node` должен поддерживать кватернион как
first-class представление поворота (`MVP-SPEC.md` §4.2 прямо требует «rotation/quaternion»), а
`Matrix4.compose` — принимать `Quaternion`. Лоадер записывает `node.quaternion.set(x,y,z,w)` без потерь.
Как временная мера допустима корректная ZYX-совместимая конвертация, но она не снимает
требование по кватерниону.

**Критерий приёмки.** Тест round-trip: для 10 случайных кватернионов матрица из
`compose(pos, scale, quat)` совпадает с эталонной матрицей поворота с точностью 1e-6.

### P1-6. Утечка GPU-ресурсов: `dispose()` удаляет только программы

**Файл:** `src/rendering/WebGLRenderer.ts`

```ts
dispose() { this.gl.deleteProgram(this.basic.program); this.gl.deleteProgram(this.lit.program); }
```

Не удаляются: VBO позиций/нормалей/UV (по 3 на геометрию), текстуры, сам контекст не теряется.
`examples/showcase.ts` вызывает `engine.dispose()` **при каждом переключении сцены** — значит при
обходе витрины утекают буферы всех 18 сцен.

Дополнительно: учёт буферов задублирован — они лежат одновременно в трёх `WeakMap` рендерера
(`uploaded`, `uploadedNormals`, `uploadedUvs`) **и** в полях самой геометрии
(`gpuBuffer`, `normalBuffer`, `uvBuffer`), причём условие заливки читает поля геометрии, а
кэш — WeakMap. Два источника истины для одного ресурса.

Ещё: `BufferGeometry.dispose(gl)` требует передать `gl` снаружи, но геометрия по архитектурному
правилу №4 (`ARCHITECTURE.md`) «не должна зависеть от renderer» — а сигнатура прямо тащит
WebGL-тип в слой геометрии.

**Требование.**

1. Ввести `ResourceCache` (владелец GPU-ресурсов, привязанный к контексту): единственный источник
   истины, `WeakMap<BufferGeometry, GeometryBuffers>` + `WeakMap<Texture2D, WebGLTexture>`.
2. Убрать поля `gpuBuffer`/`normalBuffer`/`uvBuffer` и `dispose(gl)` из `BufferGeometry`.
3. `WebGLRenderer.dispose()` освобождает **все** созданные им ресурсы и помечает себя как
   `disposed`; повторный `render()` после `dispose()` бросает понятную ошибку.
4. `Engine.dispose()` дополнительно освобождает ресурсы сцены.

**Критерий приёмки.** Тест на fake-GL: после `dispose()` число вызовов `deleteBuffer` +
`deleteTexture` + `deleteProgram` равно числу вызовов соответствующих `create*`.

### P1-7. `PostProcess` не соединяет пассы в цепочку

**Файл:** `src/rendering/PostProcess.ts`

```ts
render(input, output, gl) { let current = input; for (const pass of this.passes) { pass.apply(current, output, gl) } return this }
```

`current` объявлен, но **никогда не обновляется**. Проверено: два пасса получают один и тот же
вход `"IN"` и пишут в один и тот же выход. То есть это не цепочка, а список независимых вызовов,
каждый затирающий предыдущий. Тест в `engine.test.ts` проверяет только порядок вызовов
(`[1,2]`), поэтому баг не ловится.

**Требование.** Ping-pong между двумя FBO: пасс `i` читает результат пасса `i-1`, последний пишет
в `output`. Контракт `PostProcessPass` должен возвращать текстуру-результат либо получать
явные `read`/`write` таргеты. Если полноценный ping-pong вне текущего scope — класс должен быть
помечен `@experimental` и не экспортироваться из `index.ts` как готовая фича.

**Критерий приёмки.** Тест: 3 пасса, каждый приписывает свой id к «текстуре»; итог — `"IN>1>2>3"`.

### P1-8. UV-развёртка по умолчанию непригодна для плоскости и куба

**Файл:** `src/geometry/BufferGeometry.computePlanarUvs`

Фолбэк проецирует на плоскость **XZ**. Но `PlaneGeometry` лежит в плоскости **XY** (`z = 0`),
поэтому все `v`-координаты схлопываются в 0:

```
PlaneGeometry(2,2).uvs = 0.00,0.00, 1.00,0.00, 1.00,0.00, 0.00,0.00, 1.00,0.00, 0.00,0.00
```

Текстура растягивается в полосу. У `BoxGeometry(2)` на 36 вершин приходится **4 уникальных UV** —
боковые грани получают вырожденную развёртку.

Практическое следствие: сцена `wood-texture` (плоскость + фото дерева) показывает смазанную
полосу, `brick-texture` (куб) — растянутый по граням кирпич.

**Требование.**

1. `PlaneGeometry` и `BoxGeometry` объявляют собственные корректные UV (per-face 0..1),
   а не полагаются на фолбэк.
2. Фолбэк `computePlanarUvs` выбирает плоскость проекции по наименьшей протяжённости bbox
   (или по доминирующей оси усреднённой нормали), а не жёстко XZ.

**Критерий приёмки.** Тест: у `PlaneGeometry` 4 угловых UV — это `(0,0),(1,0),(1,1),(0,1)`;
у `BoxGeometry` ≥ 12 уникальных UV и каждая грань покрывает полный диапазон 0..1.

### P1-9. `InputMap.wasPressed()` защёлкивается навсегда

**Файл:** `src/interaction/InputMap.ts`

`pressed` очищается только вручную через `endFrame()`, но **никто** его не вызывает — ни `Engine`,
ни `examples/showcase.ts` (сцена `bounds-input` вызывает `input.bind(...).wasPressed()` в
`update`). Проверено: после `keydown` + `keyup` без `endFrame()` — `wasPressed() === true`
бессрочно.

Побочно: `bind()` создаёт **новый объект на каждый вызов**, а в showcase он вызывается
каждый кадр — мусор в hot loop.

**Требование.**

1. `Engine` владеет циклом кадра и обязан завершать кадр ввода: либо `Engine` принимает
   `InputMap` и сам зовёт `endFrame()`, либо `InputMap` подписывается на событие конца кадра.
2. `bind()` возвращает стабильный закэшированный `InputAction`-объект (по имени действия).
3. Добавить `wasReleased()` для симметрии.

**Критерий приёмки.** Тест: `keydown`→`wasPressed()===true`→`endFrame()`→`wasPressed()===false`;
`bind('jump', …) === bind('jump', …)` (референсное равенство).

## 3. P2 — архитектура и расхождения с MVP

### P2-1. Заявленная сменяемость backend-а рендера отсутствует

`ARCHITECTURE.md` и `API.md` утверждают, что `Renderer` — это backend-контракт. Фактически:

- `WebGLRenderer` **не пишет** `implements Renderer`;
- `Engine.renderer` типизирован конкретным классом `WebGLRenderer`, а не интерфейсом;
- `Engine` сам вызывает `new WebGLRenderer(canvas)` — подставить другой backend нельзя;

1. `WebGLRenderer implements Renderer`.
2. `Engine` принимает `renderer?: Renderer` либо фабрику `createRenderer(canvas)`; по умолчанию — WebGL2.
3. Логику пересчёта проекции при resize перенести в камеру: `Camera.setViewportSize(w, h)`

### P2-5. Аллокации в hot loop и качество кадрового пути

Все пункты — в коде, исполняемом **каждый кадр для каждого узла**:

| Место                                         | Проблема                                                                                                            |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `Node.updateWorldMatrix`                      | `parentMatrix.clone().multiply(...)` + `localMatrix.clone()` → 2 `Matrix4` (2 × `Float32Array(16)`) на узел на кадр |
| `Matrix4.multiply`                            | создаёт новый `Float32Array(16)` и **подменяет** `this.elements` — рвёт внешние ссылки на буфер                     |
| `Matrix4.invert`                              | то же самое                                                                                                         |
| `WebGLRenderer.render`                        | `normalMatrix()` создаёт `Float32Array(9)` на меш на кадр                                                           |
| `WebGLRenderer.render`                        | `lights.directional.flatMap(...)` — 6 новых массивов на кадр                                                        |
| `WebGLRenderer.collectLights`                 | парсинг hex-строки цвета для каждого источника **каждый кадр**                                                      |
| `WebGLRenderer.render`                        | полный `scene.traverse` дважды за кадр (свет + меши)                                                                |
| `SimplePhysics.step`, `ParticleSystem.update` | `gravity.clone().multiplyScalar()` на тело на шаг                                                                   |
| `showcase.ts`                                 | `input.bind(...)` на кадр                                                                                           |

**Требование.** Мутирующие in-place варианты (`multiplyMatrices(a, b)`, `copy`, `premultiply`),
переиспользуемые скратч-объекты, кэш распарсенного цвета в материале/свете, один обход сцены
за кадр с разделением на списки. `Matrix4.multiply` не должен подменять `elements`.

**Критерий приёмки.** Бенч-тест: 1000 узлов, 100 кадров `updateWorldMatrix` — нулевой прирост
аллокаций `Matrix4` после прогрева (счётчик в конструкторе под флагом dev).

### P2-6. Сортировка прозрачности некорректна

**Файл:** `src/rendering/WebGLRenderer.ts`

```ts
const az = a.worldMatrix.elements[14] - cameraWorld[14]; // разница мировых Z
meshes.sort((a, b) => ad - bd || (ad ? bz - az : 0));
```

Используется разница **мировых Z-координат**, а не расстояние вдоль оси взгляда камеры.
Как только камера смотрит не вдоль −Z (а `OrbitControls` вращает её всегда), порядок
прозрачных объектов становится произвольным. Непрозрачные объекты не сортируются вообще
(front-to-back дал бы выигрыш на early-Z).

**Требование.** Считать глубину как проекцию вектора «камера → объект» на forward-вектор камеры
(или брать `z` из view-space позиции). Непрозрачные — front-to-back, прозрачные — back-to-front.

### P2-7. `Raycaster` даёт только сферические пересечения

`intersectObjects` тестирует **bounding sphere**, но возвращает `point` как реальную точку
пересечения и называется `Intersection`. Клик по углу описывающей сферы куба «попадает»
в пустоту. Дополнительно `object.updateWorldMatrix(object.parent?.worldMatrix)` использует
**устаревшую** мировую матрицу родителя (её никто не обновлял до вызова).

**Требование.** Двухфазный тест: broad phase по сфере → narrow phase по треугольникам
(Möller–Trumbore) в локальном пространстве объекта, с корректной нормалью и барицентрикой в
результате. Явно документировать, если narrow phase откладывается, и переименовать метод
в `intersectBounds`.

### P2-8. `AssetManager`: `AbortSignal` и прогресс — фикция

- Первый вызов кэширует промис вместе с сигналом; повторный вызов с **другим** сигналом получает
  старый промис (проверено: возвращается закэшированное значение, новый signal игнорируется).
- Отмена по сигналу нигде не обрабатывается — при abort промис остаётся в кэше.
- `onProgress` сообщает ровно два синтетических события: `{loaded:0}` и `{loaded:1,total:1}`.
  Реального прогресса нет.

**Требование.** Реф-каунтинг подписчиков на запись кэша, отмена загрузки только при обнулении
счётчика, удаление записи из кэша при abort, прокидывание реального прогресса из загрузчика
(или удаление `onProgress` из API как несуществующей возможности).

### P2-9. `Texture2D`: необработанные ошибки и глобальное состояние GL

- `Texture2D.load` не ловит ошибку `image.decode()` → unhandled rejection при недоступном URL.

**Требование.** Опции сэмплера в конструкторе, восстановление pixel-store после загрузки,

`ResourceCache` из P1-6.

### T-5. Тест шейдеров проверяет не то

```ts
expect(source).not.toMatch(/;\s+#/);
```

`\s` включает `\n`, поэтому регэксп срабатывает на полностью корректном
`precision highp float;\n#define MAX_LIGHTS 4`. Тест падает на валидном коде — то есть
формализует несуществующее правило.

**Требование.** Проверять реальный инвариант: каждая строка, начинающаяся с `#`,
не имеет ведущих пробелов и стоит первой в своей строке (`/^[^\S\n]+#/m` не должно совпадать),
`#version` — самая первая строка. Дополнительно: тест, сверяющий список `uniform`, объявленных
в шейдере, со списком, запрашиваемым рендерером (см. P1-1).

### T-6. `-0` в `pointerToNdc`

`toEqual({x:0, y:0})` падает против `{x:+0, y:-0}`, потому что `-(0*2-1+1)` даёт `-0`.

**Требование.** Нормализовать знак нуля в самой функции (`y: y === 0 ? 0 : y` или `+ 0`) —
это корректнее, чем ослаблять тест, так как `-0` может просачиваться в дальнейшие вычисления.
